# Commit and PR Workflow

이 문서는 이 저장소의 커밋/PR 절차서다. 정책 문서가 아니라 절차 문서이며,
[`docs/ARCHITECTURE.md`](../ARCHITECTURE.md)와 충돌하면 그 문서가 우선한다.

혼자 개발하는 저장소이므로 이슈 트래킹을 커밋/PR에 강제하지 않는다. 이슈 번호는 브랜치
이름, 커밋 메시지, PR 제목, PR 본문 어디에도 요구하지 않는다.

## 1. 브랜치 이름

```
label/작업 내용 요약
```

- `label` — §2 커밋 라벨과 동일한 값 중 하나 (소문자).
- 작업 내용 요약 — 하이픈으로 구분한 영문 소문자 요약.

예: `feat/seo-indexing-and-docs`

## 2. 커밋 메시지 형식

```
label: message
```

- `label` — 아래 표의 값 중 정확히 하나만 쓴다 (소문자).
- `message` — 커밋 내용 요약.

| label      | 의미                                       |
| ---------- | ------------------------------------------ |
| `docs`     | 문서 작업                                   |
| `chore`    | 파일 이동/삭제, 의존성 추가 등 비개발 작업    |
| `feat`     | 기능 개발                                   |
| `fix`      | 오류 해결                                   |
| `refactor` | 기능 변경 없는 코드 수정                     |
| `test`     | 테스트 코드 수정                             |
| `design`   | UI 변경                                     |

다른 라벨은 쓰지 않는다. 하나의 커밋이 여러 라벨에 걸치면 라벨별로 커밋을 나눈다.

## 3. 커밋 크기

커밋당 파일 개수는 권장 10개 이하, 최대 15개를 넘지 않는다. 초과하면 논리적 경계로 나눠
여러 커밋으로 분리한다.

## 4. PR 제목 형식

```
[LABEL] title
```

- `LABEL` — §2의 커밋 라벨을 그대로 대문자로 표기 (`DOCS`, `CHORE`, `FEAT`, `FIX`,
  `REFACTOR`, `TEST`, `DESIGN`). PR에 여러 라벨의 커밋이 섞여 있으면 가장 비중이 큰
  변경을 기준으로 하나만 고른다.
- `title` — PR 내용을 요약하는 간략한 제목.

예: `[FEAT] SEO 라우팅 및 위키 초기 구조 추가`

## 5. PR 본문

`.github/PULL_REQUEST_TEMPLATE.md`의 섹션을 채운다.

- `# 🚩 연관 이슈` — 이슈 트래킹을 쓰지 않는 한 비워둔다.
- `# 📝 작업 내용` — 실제 diff 기준 요약 (원래 요청 내용이 아니라 실제 변경 사항).

## 6. 아키텍처 문서 동기화

`docs/ARCHITECTURE.md` 또는 `docs/architecture/*.md`가 다루는 내용(기술 스택, 폴더 구조,
라우팅/SEO 연동, 스타일 토큰 등)에 영향을 주는 변경이 있으면, PR을 올리기 전에 해당 문서도
함께 갱신한다. 코드와 문서가 어긋난 채로 PR을 올리지 않는다.

## 7. 커밋/PR 전 검증

CI(`.github/workflows/CI.yml`)는 PR 시점에 다음만 실행한다.

```bash
npm run test
npm run lint
```

**CI가 실행하지 않는 것**: `npm run build`(`tsc -b && vite build`, 타입체크 포함)는 CI에
없다. 타입 오류를 배포 전에 잡으려면 로컬에서 직접 `npm run build`를 돌려야 한다.

## 8. Push/PR 생성 — 확인 게이트

커밋 요청은 원격 push 권한을 포함하지 않는다. push나 PR 생성 전에는 실제로 무엇을
push하는지(브랜치, 커밋, 대상 브랜치)를 사용자에게 알리고 명시적 확인을 받는다 — 변경
내용과 검증 결과를 실제로 확인한 뒤에 물어보고, 미리 묻지 않는다.
