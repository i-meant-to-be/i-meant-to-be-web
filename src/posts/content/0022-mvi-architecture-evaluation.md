## 배경

[이전 포스트](/post/0021-mvi-architecture-splitting-viewmodel)에서 개선한 MVI 아키텍처에 어떤 변화가 있었는지, 또 어떤 구성 요소가 추가되었고 이들이 어떻게 뷰 모델의 비대함을 해결했는지를 살펴보았다. 이번 게시물에서는 이 작업이 과연 그럴 만한 가치가 있는지를 살펴보도록 하겠다.

## 요약

먼저, 이전 포스트에서 설명했던 개편된 MVI 아키텍처의 구성 요소를 다시 한 번 짚어보자.

|구성 요소|역할 또는 책임|
|---|---|
|Intent|사용자 행동, 화면 수명 변화, 장치 작업 결과 등 외부 입력|
|ViewModel|인텐트를 분류하고 그에 따른 후속 작업을 연결하는 중간 관리자|
|Handler|특정 책임에 관한 작업을 수행하는 담당자|
|Mutation|상태가 갱신되어야 하는 사유와 변경에 필요한 값|
|Reducer|현재 상태와 Mutation을 받아 다음 상태를 계산하는 함수|
|State|화면의 현재 상태|
|Effect|화면에서 한 번만 수행되어야 할 동작을 요청하는 메시지|
|Context|Handler가 상태 조회, 변경, Effect 발행, 작업 실행에 쓰는 일종의 경로|
|Workflow|다른 책임으로 이어져야 함을 명시하는 내부의 후속 작업 흐름|

### 기존에 존재했던 요소

기존 MVI 아키텍처에서 사용했던 요소들은 다음과 같다:

- Intent
- ViewModel
- State
- Effect

이 4가지는 대부분의 Android MVI 아키텍처라고 하면 쉽게 찾아볼 수 있는 구성 요소들이고, 실제로도 위 4가지만 가지고도 웬만한 화면과 뷰 모델은 충분히 구현 가능하다. 다시 말해, 이 작업의 관건은 **위 4가지만으로 뷰 모델을 충분히 구성할 수 있었는가**?라는 질문에 대한 답으로 결정되겠다.

### 새로 추가된 요소

이번 작업으로 새로 추가된 요소들은 다음과 같다:

- Handler
- Mutation
- Reducer
- Context
- Workflow

차례대로 간단히 살펴보자.

Handler는 **수많은 인텐트의 하위 분류**를 맡는다. 문제가 됐던 화면은 1개로 면접 화면이었지만 세부 기능은 질문-답변 턴 관리, 녹화, 세션 유지 등 여러 개로 나눌 수 있었다. 하나의 앱을 여러 기능으로 나눈다면, Handler는 하나의 기능을 여러 세부 책임으로 나눈 셈이다.

Mutation은 **상태 변경 사유와 그 값**을 맡는다. 개선 전에는 수많은 `private fun` 함수들과 뷰 모델의 단일 인텐트 처리 함수 `onIntent`의 여러 분기에 상태를 갱신하는 코드가 산개되어 있었다. 그래서 어떤 지점에서 어떤 원인에 의해 상태 갱신이 발생하는지 추적하기 어려웠다. Mutation은 여러 지점에 산개되어 있던 상태 갱신 사유를 명확하게 추적하기 위해 도입되었다.

Reducer는 **현재 상태와 Mutation을 받아 다음 상태를 갱신**한다. 다음 상태를 계산하는 규칙만 딱 떼서 순수하게 Reducer로 분리하면, 비즈니스 로직에 대한 단위 테스트가 가능해지고 더 나아가 Handler에 따른 갱신 원인도 하위 분류로 묶어줄 수 있다. 예를 들어 질문-답변의 한 차례를 턴(turn)이라고 부를 경우, `TurnHandler`에서 상태를 갱신하는 규칙을 `InterviewReducer` 내부의 `reduceTurn` 함수에 두는 식으로 대응을 시킬 수 있다는 말이다.

Context는 **모든 신규/기존 구성 요소를 묶고 상태 관리를 단일 창구에서 진행**하기 위한 일종의 문맥이다. 여러 구성 요소들이 매우 긴밀하게 엮여 있고, 모두가 공유하는 단 하나의 상태 인스턴스를 유지하면서 원자적으로 상태를 갱신하기 위해 필요하다.

Workflow는 **여러 하위 책임 간 연계를 코드 수준에서 설명**하기 위해 도입되었다. 위에서 언급한 턴을 다시 꺼내오면, 한 번의 질문과 답변 사이에는 영상 녹화, API를 통한 사용자 답변 서버로 전송 그리고 로컬 저장소에 세션 데이터 저장 등 다양한 작업이 필요한 순서에 의해 이어진다. 그리고 이 작업들은 서로 다른 Handler들이 맡은 세부 책임에 걸쳐서 진행될 때가 많다. 이처럼 여러 이해관계자에 걸쳐 있는 작업을 매끄럽게 코드 수준에서 묘사하기 위해 Workflow가 도입되었다.

### 적용된 변경 사항

위 구성 요소들을 바탕으로, 이 개선 작업에서는 다음 변경 사항들을 적용했다:

- 기존 뷰 모델 기반 클래스 `MviViewModel`에서 `reduce` 함수 제거
- 제거한 `reduce` 함수를 대체하는 별도의 `Reducer`를 비롯한 5건의 신규 구성 요소 도입
- 앱 내 15개 화면 전체 ViewModel에 개선된 MVI 아키텍처 일괄 적용

## 평가

자, 그럼 위 변경 사항에 대한 나의 적합성 진단은 어떨까? 답은 "**개선은 합리적이었으나 일부 불필요한 부분이 있고 뷰 모델이 작을 경우 적용하지 않는 게 오히려 낫다**"로 정리할 수 있을 것 같다.

### 비대한 뷰 모델에서는 합리적인 개선

위 개선은 뷰 모델에 **수많은 인텐트와 상태 갱신 로직이 산개**되어 있을 때 효과를 본다. 상태 갱신 규칙과 사유 등 모든 것들을 구성 요소로 명시하기 때문이다. 그래서 본 프로젝트의 면접 화면에서 특히 개선 사항 적용을 통한 실익이 컸다. 기존 1,262줄에서 개선 후 218줄까지 줄었다. 조건을 모두 충족했기 때문이었다.

또한 위에서 모든 화면에 적용이 되었다고 언급했던 바 있는데, 면접 화면 외에도 다양한 생명주기를 갖는 기능들이 겹친 온보딩 화면(919줄 → 160줄), 마이 페이지 화면(716줄 → 195줄)에서도 어느 정도 효과가 있었다.

### 덜어내야 할 부분

다만 아키텍처에서 덜어낼 수 있는 부분이 있다면 **Workflow**가 될 수 있을 것 같다.

나머지 4가지(Handler, Mutation, Reducer, Context)는 각자의 역할이 명확하여 분리할 만하거나, 이미 다른 프레임워크에서 사용되고 있어 분리할 명분이 충분했다. 반면, Workflow는 단순히 여러 기능이나 Handler 간 연결을 코드 수준에서 명시한 것에 지나지 않는다. 그렇기에 Workflow 없이 구현하여 자연스럽게 흐름이 보이도록 하는 것과 비교했을 때 큰 효능감을 주는 것도 아니며, 하다못해 프로젝트나 앱 정책 위키 또는 문서에서 명시해도 충분했다. 다시 말해 분리해도 분리를 안 하는 경우와 비교했을 때 이익이 크지 않다는 점이다.

실제 코드도 이 짐작과 맞아 떨어졌다. 개선 사항을 적용한 15개 화면 중에서 Workflow를 도입한 화면은 오직 면접 화면 뿐이었는데 이거 하나만을 위해 불필요한 구성 요소를 아키텍처에 포함할 필요까지는 없었다. 또한, 서로 책임이 다른 여러 Handler 간 중재는 기존과 같이 ViewModel이 맡았어야 하는데, 일정 부분을 Workflow가 맡게 되면서 두 구성 요소 간 책임 소재가 흐려진 것도 문제라면 문제라고 할 수 있다.

### 뷰 모델이 작을 경우에는 불필요

이 개선을 적용하게 된 주된 동기는 뷰 모델이 너무 비대해졌기 때문이었다. 그리고 뷰 모델의 비대화는 곧 상태 갱신의 추적과 원인이 된 인텐트를 추적하기 어렵게 만든다. 반대로 말해, 뷰 모델이 복잡하지 않아 이 개선을 적용하지 않고 ViewModel, Intent, Effect, State 만으로도 로직을 충분히 드러낼 수 있는 경우, 굳이 추상화와 아키텍처의 복잡함을 감수하면서 적용할 필요가 없다는 것이다.

그러나 안타깝게도 본 앱의 모든 뷰 모델이 기반 뷰 모델 클래스인 `MviViewModel`에 의존하고 있었기 때문에, 이 개선 사항은 면접 화면 외 다른 화면에도 모두 같이 적용되었다. 면접 화면에 한해서는 의미가 있었을지 모르나, 다른 비교적 간단한 화면들에서는 보일러플레이트가 약 2배 정도 늘어났다:

|화면|코드 감소량|코드 증가량|총 변화량|
|---|---|---|---|
|스플래시 화면|-22|+69|+45|
|권한 동의 화면|-12|+34|+22|
|약관 동의 화면|-62|+120|+58|
|피드백 화면|-65|+157|+91|
|면접 보고서 화면|-70|+159|+89|

보일러플레이트가 생각보다 많이 증가했기 때문에, 면접 화면에서만 선택적으로 개선 사항을 적용하는 것이 더 낫지 않았을까... 하는 생각이 드는 지점이었다.

## 결론

따라서 본 개선은 **면접 기능에 한해서는 합리적인 개선**이었으며, 다만 다음 작업에서 가능하다면 **Workflow를 제거**하고 **뷰 모델이 비대하지 않은 다른 화면은 기존 아키텍처로 복구**하는 것이 나을 수 있다는 결론으로 마무리를 지을 수 있을 것 같다.

요즘 코드를 AI가 쳐 주기 때문에 명령을 내리는 인간의 의도와 설계가 그만큼 더 중요해졌다. 따라서 내가 어떻게 지침을 줄지 심도 깊게 고민해보고, AI가 작성한 코드를 그냥 넘기는 대신 내가 지시한 부분이 잘 지켜졌는지, 의도와 다르게 반영된 부분은 없는지 점검해보는 습관이 중요할 것 같다.
